Upstream cvxpy 1.9.2: stock canon backends on the DPP path vs ignore_dpp
========================================================================
Date:    2026-08-08
Machine: MacBook Pro (15-inch, 2018), 6-core Intel i7-8850H @ 2.60GHz, 16 GB,
         macOS 15.7.7. BLAS pinned to 1 thread (OMP/OPENBLAS/MKL/VECLIB=1).
Env:     canonicalization/.venv-upstream -- STOCK upstream cvxpy 1.9.2,
         Python 3.14, numpy 2.5.1, scipy 1.18.0. Isolated on purpose: cvxpy
         1.9.2 pins sparsediffpy<0.4.0, which would clobber the 0.7.0 dev
         build in .venv. Upstream has NO diff-engine backend.

Why this run exists
-------------------
The published backend tables compare the diff engine (ignore_dpp=True: keeps
the expression tree, emits concrete (P,c,A,b) for one parameter value) against
CPP/SCIPY/COO on the DPP path (which build a parameter->data TENSOR). Those are
different jobs, so the cold ratios partly measured "tensor vs tree", not backend
quality. The *_ND columns are the same backends with ignore_dpp=True, where
EvalParams bakes the parameters in and the backend emits a plain matrix -- the
SAME artefact the engine produces. The diff-engine fork cannot run this: it
raises ValueError for an explicit canon_backend on the ignore_dpp path, which is
why stock upstream cvxpy is required.

Artefact equivalence was verified separately (verify_nodpp_equivalence.py):
fork DIFFENGINE vs upstream CPP_ND MATCH on ConvexPlasticity,
ParamConeMatrixStuffing and ParamSmallMatrixStuffing -- A bit-identical
(max|diff|=0), P to 5.55e-17.

Reading the numbers
-------------------
* CONTROL: 17 of 25 problems are parameter-free, where ignore_dpp is a no-op,
  so X and X_ND must agree. They do, but the spread is 0.74x-1.18x -- that is
  the noise floor of this machine on a single un-replicated timing. Nothing
  below ~1.25x is meaningful here; the parametric effects below are 15-30x.
* The cold tensor cost scales with PARAMETER SIZE, not problem size:
    ParamSmallMatrixStuffing (90,450 param entries)  CPP 7.90 -> CPP_ND 0.29
    ParamConeMatrixStuffing  (40,300)                CPP 3.25 -> CPP_ND 0.18
    SVMWithL1 / SimpleScalarParamLP / FactorCov (1-2) no difference (0.96-1.03x)
* ConvexPlasticity is NOT DPP (see the dpp? column, now computed with the
  chain's predicate), so EvalParams is inserted regardless and all six columns
  agree at ~0.35 s.
* CPP is often SLOWER than the pure-Python SCIPY backend: 59.8 vs 8.6 s
  (SDPSegfault1132), 20.4 vs 2.7 (Cajas), 16.2 vs 10.8 (SimpleQP).

Gaps
----
* SimpleFullyParametrizedLPBenchmark (10^6 param entries): crashed/killed under
  a PINNED CPP backend. Isolated repro: with no canon_backend cvxpy routes to
  COO (>= DPP_PARAM_THRESHOLD) and finishes in seconds at 558 MB peak; pinned
  CPP did not finish in >6 min, with 0.3-2.1 GB of allocation churn. The harness
  worker died with no Python exception (consistent with an OOM kill, though the
  exact kill mechanism is unconfirmed). Same failure on the fork -- see the
  bridge file. This is precisely the case DPP_PARAM_THRESHOLD exists to avoid.
* ParametrizedQPBenchmark (1.4e7 param entries): excluded. Under pinned CPP it
  took down the whole run once; not re-attempted.
* Merged from two runs (the first was killed mid-sweep at problem 19); the
  per-problem parts are *_20260808.txt and *_20260808_part2.txt.

=======================================================================
Source:  https://github.com/cvxpy/benchmarks (cloned, run as is)
cvxpy:   1.9.2   python: 3.14.4   platform: darwin
timeout: 2400s/problem   solver=CLARABEL (uniform, for comparability)
backends: CPP,SCIPY,COO,CPP_ND,SCIPY_ND,COO_ND
strategies: dpp,dpp_coo,dpp_scipy,nodpp_cpp,nodpp_scipy,nodpp_coo

Table 1 = COLD first-compile time (s) of each problem under each canon backend
  (fresh setup + get_problem_data per backend, since the chain cache key
  excludes canon_backend).
Table 2 = re-compile time (s) with changing parameters (parametric problems
  only), mean of 3, fresh instance per strategy.
The last column of each table is a configurable ratio (BENCH_RATIO,
BENCH_RATIO_WARM); <1 means the numerator is faster.

Targets (the get_problem_data kwargs each column selects):
  CPP/SCIPY/COO      explicit canon_backend, DPP path -- builds the
                     parameter->data TENSOR (only worth it across re-solves).
  CPP_ND/SCIPY_ND/   same backend with ignore_dpp=True: EvalParams bakes the
  COO_ND             parameters into constants, so the backend builds a plain
                     non-parametric matrix -- the SAME artefact the diff engine
                     produces, hence the like-for-like comparison. Upstream
                     cvxpy only: the fork rejects an explicit backend here.
  CPP_DEFAULT        no canon_backend at all. NOT the same as CPP: cvxpy
                     silently switches to COO once total parameter size >=
                     DPP_PARAM_THRESHOLD (1000). Kept only to replicate
                     results published before the CPP column was pinned.
  DIFFENGINE         ignore_dpp=True with no explicit backend (diff-engine fork).
  DE_DPP             explicit canon_backend=DIFFENGINE on the DPP path.
  dpp/diffengine/    warm strategies; nodpp_* are the ignore_dpp=True variants,
  de_cached/dpp_*/   where cvxpy sets uncached_param_prog and every re-solve is
  nodpp_*            a FULL recompile -- i.e. the cost of not having DPP.
'dpp?' is is_dpp() as the solving chain evaluates it (quad_form_dpp='qp' for
solvers that take a quadratic objective), which is what decides the branch --
not the bare problem.is_dpp() older tables reported.
