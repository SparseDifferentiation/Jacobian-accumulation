Upstream cvxpy/benchmarks suite: MEMORY of canonicalization backends
=====================================================================
Source:  https://github.com/cvxpy/benchmarks (cloned, run as is)
cvxpy:   1.9.2   python: 3.14.4   platform: darwin
timeout: 1200s/measurement   solver=CLARABEL   warm iters=3
backends: CPP_ND,SCIPY_ND,COO_ND
strategies: diffengine,de_cached,dpp,dpp_coo,dpp_scipy

Metric: peak-RSS high-water delta (MB) of ONE isolated subprocess per
(problem, backend/strategy). gc.collect + ru_maxrss snapshot after setup
(cold) / after the cache-populating warmup compile (warm), run the measured
region, snapshot again; the delta is the memory attributable to the region.
ru_maxrss is monotone: '*' marks regions that never exceeded the prior
high-water mark -- the value is a floor, not a true peak (see retained_mb
in the raw JSON).

Table 1M = COLD first-extraction peak (MB) per canon backend. The last
  column is a configurable ratio (BENCH_RATIO); <1 = numerator leaner.
  It is suppressed when either side is a floor rather than a true peak.
Table 2M = ADDITIONAL peak (MB) during 3 warm re-solves with fresh
  parameter values, after the warmup compile (parametric problems only).
Table 3M = the diff engine's self-reported allocation peak (MB), from its
  sp_malloc counters (g_peak_bytes; engine-internal allocations only --
  CVXPY front-end / scipy / numpy memory is invisible to it). 'rss' is the
  matching process-level delta from Tables 1M/2M; the gap is glue memory
  outside the engine. g_peak_bytes resets at each capsule construction, so
  warm diffengine values are the per-re-solve capsule peak, warm de_cached
  values the peak since the cached capsule was built.
  Empty on upstream cvxpy, which has no diff-engine backend.

Targets (the get_problem_data kwargs each column selects):
  CPP/SCIPY/COO      explicit canon_backend, DPP path -- builds the
                     parameter->data TENSOR (only worth it across re-solves).
  CPP_ND/SCIPY_ND/   same backend with ignore_dpp=True: EvalParams bakes the
  COO_ND             parameters into constants, so the backend builds a plain
                     non-parametric matrix -- the SAME artefact the diff engine
                     produces, hence the like-for-like comparison. Upstream
                     cvxpy only: the fork rejects an explicit backend here.
  CPP_DEFAULT        no canon_backend at all. NOT the same as CPP: cvxpy
                     silently switches to COO once total parameter size >=
                     DPP_PARAM_THRESHOLD (1000). Kept only to replicate
                     results published before the CPP column was pinned.
  DIFFENGINE         ignore_dpp=True with no explicit backend (diff-engine fork).
  DE_DPP             explicit canon_backend=DIFFENGINE on the DPP path.
  dpp/diffengine/    warm strategies; nodpp_* are the ignore_dpp=True variants,
  de_cached/dpp_*/   where cvxpy sets uncached_param_prog and every re-solve is
  nodpp_*            a FULL recompile -- i.e. the cost of not having DPP.
'dpp?' is is_dpp() as the solving chain evaluates it (quad_form_dpp='qp' for
solvers that take a quadratic objective), which is what decides the branch --
not the bare problem.is_dpp() older tables reported.
