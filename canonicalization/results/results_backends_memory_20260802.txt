Raw per-child JSON (pre/post ru_maxrss, current-RSS retained_mb, engine

VERDICT: memory is NOT uniformly in the engine's favor. The engine is leaner
on stuffing/QP/portfolio shapes (UnconstrainedQP 0.05x, Murray 0.14x,
ConeMatrixStuffing 0.41x, SmallMatrixStuffing 0.45x, Huber 0.70x, LeastSquares
0.79x) but much heavier where the dense-block pathology lives (cold, vs CPP):
OptimalAdvertising 34.3x (5.1 GB vs 150 MB), CVaRBenchmark 6.8x (4.6 GB),
QuantumHilbertMatrix 3.7x, SemidefiniteProgramming 3.0x, TvInpainting 1.9x --
and Table 3M shows those peaks are ENGINE-INTERNAL (CVaR: 8.9 GB engine-side
alloc peak; OptimalAdvertising: 5.9 GB). Mechanism (OptAdv, probed 2026-08-02
via staged g_peak snapshots + source trace): NOT accumulation and NOT dense
values -- 100% of the memory is allocated and retained in jacobian_init, and
it is per-block index METADATA: each kron block of a dense-vector matmul
Jacobian (D@ones: m blocks; D.T@ones: n blocks) is an independent
permuted_dense carrying a col_inv array over the FULL n_vars column space
(permuted_dense.c:605), replicated again by every copy_sparsity/transpose/
reshape node in the chain, plus a per-branch n_vars-sized CSC cache
(sparse_matrix.c:71). Measured law: ~20 B x (m+n) x mn; predicts 6.5 GB vs
5.9 measured. Values and the final CSR pattern are exact-nnz throughout.
This is an ENGINEERING fix (share col_inv across blocks, or hash/binsearch
col_perm), not a paradigm limit. Timing hid it: engine cold was 0.87x CPP on
OptAdv while using 34x the memory. Warm
re-solves are near-free for every strategy (<=2.6 MB additional) except
ConvexPlasticity (~71 MB/loop on all strategies -- the known zero-padded-P
scipy re-sort glue). cvxcore-side anomalies worth debugging: SCIPY backend
needs 243 MB / 685 MB cold on the tiny ParamConeMatrixStuffing (200 vars) /
ParamSmallMatrixStuffing (300 vars) where CPP needs 7 / 17 MB, and SCIPY
crashed (SimpleFullyParametrizedLP) or timed out >1200 s (ParametrizedQP);
CPP needs 2.7 GB on gini Murray where every other backend needs ~0.3-0.4 GB,
and 1.1 GB on the 18-variable UnconstrainedQP (engine: 50 MB).

Caveat (macOS): engine self-reported live-byte peaks can EXCEED the process
RSS delta (CVaR 8.9 GB engine vs 4.6 GB RSS) -- ru_maxrss deltas undercount
when setup() already set a high-water mark and macOS compresses cold dirty
pages; treat RSS deltas as floors and the engine counters as exact for
engine-internal allocations.

=====================================================================
Source:  https://github.com/cvxpy/benchmarks (cloned, run as is)
cvxpy:   0.1.0.dev3996+gca08a26d1   python: 3.14.4   platform: darwin
timeout: 1200s/measurement   solver=CLARABEL   warm iters=3

Metric: peak-RSS high-water delta (MB) of ONE isolated subprocess per
(problem, backend/strategy). gc.collect + ru_maxrss snapshot after setup
(cold) / after the cache-populating warmup compile (warm), run the measured
region, snapshot again; the delta is the memory attributable to the region.
ru_maxrss is monotone: '*' marks regions that never exceeded the prior
high-water mark -- the value is a floor, not a true peak (see retained_mb
in the raw JSON).

Table 1M = COLD first-extraction peak (MB) per canon backend.
  'd/CPP' = DIFFENG / CPP (<1 = diffengine leaner).
Table 2M = ADDITIONAL peak (MB) during 3 warm re-solves with fresh
  parameter values, after the warmup compile (parametric problems only).
Table 3M = the diff engine's self-reported allocation peak (MB), from its
  sp_malloc counters (g_peak_bytes; engine-internal allocations only --
  CVXPY front-end / scipy / numpy memory is invisible to it). 'rss' is the
  matching process-level delta from Tables 1M/2M; the gap is glue memory
  outside the engine. g_peak_bytes resets at each capsule construction, so
  warm diffengine values are the per-re-solve capsule peak, warm de_cached
  values the peak since the cached capsule was built.
